===============================================================================
                       PROJECT ODIN: AI OPERATIONAL MANUAL
===============================================================================

This document outlines the architecture, execution flow, and management of the
locally isolated, multi-agent AI system running via Termux.

-------------------------------------------------------------------------------
1. SYSTEM ARCHITECTURE & COMPONENTS
-------------------------------------------------------------------------------
The architecture relies on a "Claim-Check" routing pattern using a local SQLite 
database (`odin_archive.db`) to safely track file states without memory leaks.

* odin_daemon.py    : The central automation engine. Runs an infinite loop 
                      every 15 seconds to look for new assets.
* ingest_manager.py : Discovers staged assets and assigns unique SHA-256 hashes.
* analyzer_agent.py : Powers the local LLM interface via Ollama REST API.
* vision_agent.py   : Native binary header parser for image assets.
* muninn_text.py    : Injection script (Memory) to drop raw text into staging.
* huginn_thought.py : Retrieval script (Thought) to read processed intelligence.

-------------------------------------------------------------------------------
2. INITIALIZATION SEQUENCE (STARTING THE SYSTEM)
-------------------------------------------------------------------------------
To start the entire automated matrix from a fresh boot, follow these steps across
separate terminal panes or background jobs:

Step 1: Spin up the local inference backend
    $ pkill ollama
    $ ollama serve &

Step 2: Start the background automation daemon
    $ cd ~/Lloyd/ai
    $ python odin_daemon.py &

-------------------------------------------------------------------------------
3. DATA INJECTION (MUNINN / MEMORY)
-------------------------------------------------------------------------------
To feed text, logs, or notes into Project Odin's context without interrupting 
the daemon loop, use the Muninn script:

Command Line String:
    $ python muninn_text.py "Your custom text or raw asset log details here."

Programmatic Import:
    from muninn_text import dispatch_muninn
    dispatch_muninn("Automated payload from external scraper scratchpad.")

* Result: Muninn writes a timestamped file into `odin_ai/staging/`. Within 15
  seconds, the daemon detects it, hashes it, and feeds it to the local LLM.

-------------------------------------------------------------------------------
4. INTELLIGENCE RETRIEVAL (HUGINN / THOUGHT)
-------------------------------------------------------------------------------
To view the structural summaries and extracted keywords generated by the 
resource-constrained model cluster, summon Huginn:

    $ python huginn_thought.py

* Result: Spits out a scannable console printout of all 'Analyzed' assets, 
  ordered chronologically with Asset IDs and truncated SHA-256 identifiers.

-------------------------------------------------------------------------------
5. TROUBLESHOOTING & MEMORY MANAGEMENT (HTTP 500 / TIMEOUTS)
-------------------------------------------------------------------------------
Because processing happens locally on mobile hardware, resource contention or 
stuck inference slots can trigger HTTP 500 errors on the `/api/generate` endpoint.

If Huginn logs "LLM Error: Could not reach Ollama service. Details: timed out":

1. Verify the current execution target model (Default: qwen2.5-coder:0.5b)
    $ ollama list

2. Clear stuck memory allocations and reset the DB flags back to raw state:
    $ pkill ollama
    $ ollama serve &
    $ python -c "import sqlite3; conn=sqlite3.connect('odin_ai/db/odin_archive.db'); c=conn.cursor(); c.execute(\"UPDATE file_archive SET processing_status='Indexed', profile_summary=NULL\"); conn.commit(); conn.close(); print('[+] DB Reset.')"

3. Manually force a single-pass processing test to verify stability:
    $ python analyzer_agent.py
